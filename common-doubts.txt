✅ Custom Structural Directive (example)

👉 Show element only if role is ADMIN

@Directive({
  selector: '[appHasRole]'
})
export class HasRoleDirective {
  constructor(
    private tpl: TemplateRef<any>,
    private vcr: ViewContainerRef
  ) {}

  @Input()
  set appHasRole(role: string) {
    if (role === 'ADMIN') {
      this.vcr.createEmbeddedView(this.tpl);
    } else {
      this.vcr.clear();
    }
  }
}

Style priority order (VERY important)

From lowest → highest priority:

Browser default styles

styles.css (global)

Component styles (.component.css)

Inline styles (style="")

!important 😈

Behind the scenes — step-by-step (what Angular actually does)

I’ll show the typical pipeline using Emulated (because it’s the default), then contrast with ShadowDom and None.

Emulated (step-by-step)

Compile and fingerprint the component

Angular assigns a short unique ID for the component at compile time (example tokens: something like c0, c1, etc.). You’ll see attributes like _ngcontent-c0 and _nghost-c0 in the DOM. (Names may vary with Angular versions.) 
Angular

Transform CSS selectors

Angular rewrites each selector by adding the matching attribute.

Example: button { color: red } → button[_ngcontent-c0] { color: red }

Add attributes to DOM nodes

When rendering the component, Angular adds the matching _ngcontent-c0 attribute to elements inside the component template and _nghost-c0 (or similar) to the host element.

Inject scoped stylesheet into <head>

The transformed (scoped) stylesheet is injected into <head> as a <style> tag. Because selectors include the unique attribute, they only match nodes inside that component.

Result: component styles affect internal elements only (they won’t match elements without the _ngcontent-* attribute). But global rules (like div { margin:0 } in styles.css) still match normal tags and therefore can style inside elements because the global rule has no attribute and the browser still sees the element tag.

ShadowDom (step-by-step)

Create a shadow root on the host element at component bootstrap: host.attachShadow({mode: 'open'}).

Move component DOM into the shadow root — the template renders inside the shadow root.

Place component styles inside shadow root — browser applies them only to content inside that shadow root.

Result: true encapsulation — outside CSS doesn’t apply inside shadow, and component styles do not leak out. You can expose style hooks via CSS custom properties or ::slotted() to style projected content. 
MDN Web Docs
+1

None (step-by-step)

Take component CSS as-is (no rewriting).

Inject into global <head> — stylesheet behaves like any global stylesheet.

Result: styles apply globally like styles.css. Easy but risky for collisions. 
Angular

How styles.css (global stylesheet) interacts with each mode

Emulated: Global CSS can affect inside elements (because global rules are not scoped). Component styles won’t affect outside. So global rules can "pierce" the component. 
angular.io

ShadowDom: Global CSS generally cannot affect content inside the shadow root. Exceptions: CSS custom properties (variables) cross the boundary, and ::part / ::slotted and styling applied to the host element can affect or be used to tune internals. 
MDN Web Docs

None: Global styles.css and component styles are the same pool — everything affects everything.

1️⃣ ::ng-deep (Angular’s forbidden tunnel 🚫)
What is ::ng-deep?

::ng-deep tells Angular:

“Ignore view encapsulation and apply this style deep into child components.”

::ng-deep app-child button {
  color: red;
}


➡️ Parent component styles pierce child component styles

Why did it exist?

Before Shadow DOM support matured:

Angular used Emulated encapsulation

Parent couldn’t style child internals

Devs needed a way to break rules

So Angular gave a backdoor

How it works (behind the scenes ⚙️)

In Emulated encapsulation:

::ng-deep button {
  color: red;
}


Angular compiles it to something like:

button {
  color: red;
}


✅ Removes _ngcontent scoping
✅ Turns it into global CSS

💥 That’s why it’s dangerous

Why is ::ng-deep deprecated?

Because:

❌ Breaks component isolation

❌ Hard to maintain

❌ Causes random CSS bugs

❌ Not compatible with real Shadow DOM

Angular team says:

“If you need ::ng-deep, your component design is leaking.”

📌 It still works today, but will be removed

✅ When (rarely) acceptable

Styling Angular Material internals

Temporary legacy fixes

Migration projects

❌ Never for new architecture

2️⃣ CSS Variables (✅ THE BEST solution)
What are CSS variables?

They are runtime values that flow from parent → child → shadow root

:root {
  --primary-color: blue;
}

button {
  color: var(--primary-color);
}

Why variables work across Shadow DOM?

✅ Variables are inherited
✅ Inheritance crosses shadow boundaries
✅ Browser allows it by design

This is intentional, safe tunneling

Behind the scenes 🧠

When browser computes CSS:

Host element has --primary-color

Shadow root inherits it

Shadow CSS can consume it

No selector crossing needed

✅ No encapsulation break
✅ Fully standards-compliant

Angular example (recommended ✅)
/* styles.css */
app-button {
  --btn-bg: green;
}

/* inside shadow component */
button {
  background: var(--btn-bg);
}


💡 This is how Angular Material theming works internally

What is ::part()?

A Web Components feature that allows a component to explicitly expose elements for styling.

Inside Shadow DOM:

<button part="action">Save</button>


Outside:

app-button::part(action) {
  background: red;

Why does it exist?

Because:

Full isolation is too strict sometimes

But full access is dangerous

So browser designers said:

“Expose only what you want to be styleable.”

How it works behind the scenes ⚙️

Browser keeps a whitelist of exposed elements

::part() selectors can match only those

No DOM access

No deep traversal

✅ Safe
✅ Explicit
✅ Future-proof

Angular + ::part()

Works only when using ShadowDom

When to use

✅ Design Systems
✅ Shared UI libraries
✅ Button / card / input components

4️⃣ Slots (<slot> and ::slotted())
What is a slot?

Slot is a placeholder inside Shadow DOM that accepts external content

<!-- Parent -->
<app-card>
  <h2>Title</h2>
</app-card>

<!-- app-card -->
<slot></slot>

How slots actually work 🧩

Content stays in Light DOM

Browser projects it visually into Shadow DOM

Ownership does NOT change

That’s key 🔥

Styling slotted content

Inside shadow CSS:

::slotted(h2) {
  color: blue;
}


✅ Allowed
❌ But limited

BIG limitation ⚠️

❌ You cannot do:

::slotted(h2 span) { ... } ❌


Why?

Slotted content is not part of shadow DOM tree
Browser only allows top-level matching

1️⃣ First idea: What problem does slot solve?

Slot is about CONTENT, not styles.

It answers this question:

👉 “How can a component accept HTML from outside and decide WHERE it should appear inside?”

In Angular terms:

Slot ≈ content projection

Slot ≈ <ng-content>

✅ Concept is same

✅ Implementation is browser-level

2️⃣ Light DOM vs Shadow DOM (this is the key 🔑)
Light DOM

This is the normal HTML written by the parent.

<app-card>
  <h2>Title</h2>
  <p>Description</p>
</app-card>


👆 This content belongs to the parent

Shadow DOM

This is the internal DOM created by the component.

#shadow-root
  <div class="card">
    <slot></slot>
  </div>


👆 This belongs to the component

What slot actually does

The browser:

✅ Keeps content in Light DOM
✅ Visually injects it into Shadow DOM
✅ Using <slot>

This is called projection, not moving.

3️⃣ Step-by-step: How <slot> really works
Step 1 – Parent provides content
<app-card>
  <h2>Hello</h2>
  <p>Welcome</p>
</app-card>

Step 2 – Component defines slots
<!-- inside shadow DOM -->
<div class="card">
  <slot></slot>
</div>

Step 3 – Browser projection magic ✨

Result in browser rendering, not DOM move:

app-card (host)
  h2        ← still Light DOM
  p         ← still Light DOM
  #shadow-root
    div.card
      slot (projects h2, p visually)


✅ Content appears inside card
✅ Ownership unchanged

4️⃣ Named slots (multiple holes 🕳️)
Parent
<app-card>
  <h2 slot="title">My Title</h2>
  <p slot="content">Text</p>
</app-card>

Shadow DOM
<div class="card">
  <header>
    <slot name="title"></slot>
  </header>
  <main>
    <slot name="content"></slot>
  </main>
</div>


🧠 Browser matches:

slot="title" → <slot name="title">

slot="content" → <slot name="content">

Remaining content goes to default slot

5️⃣ Now the BIG confusion: ::slotted()
What is ::slotted()?

It is a CSS selector used INSIDE Shadow DOM
Used to style projected Light DOM content

::slotted(h2) {
  color: red;
}


✅ Styles <h2> that comes from parent
✅ Only applies after projection

6️⃣ Why can’t we style deeper? (MOST IMPORTANT PART)

❌ This does NOT work:

::slotted(h2 span) {
  color: blue;
}

Why?

Because:

Slotted content is not part of shadow DOM

Browser gives read-only access to top-level nodes

You’re allowed to style the host element only

Not its children

Think of ::slotted() as:

“I can touch the envelope, not the letter inside.”

7️⃣ Mental model (this will lock it in 🧠)
Slot = window
Slotted content = someone standing behind the window

You can:
✅ Paint the person’s clothes (top-level)
❌ Not their inner organs (children)

8️⃣ Slot vs ng-content (Angular clarity)
Angular	Shadow DOM
<ng-content></ng-content>	<slot></slot>
select	slot="name"
Angular-controlled	Browser-controlled
Emulated	Real Shadow DOM

Angular ng-content:

Content becomes part of component view

Styles can target deeply (with emulated trickery)

Slot:

Content stays external

Strict styling rules
